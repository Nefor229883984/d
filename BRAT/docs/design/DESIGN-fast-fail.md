DESIGN-fast-fail — быстрый и честный отказ: рекурсия

Статус: дизайн, не реализация. Ничего здесь не внедрено; каждый вариант
называет цену и выигрыш, рекомендация аргументирована. Все факты — со
ссылками `file:line`; числа, помеченные «измерено здесь», получены на этой
машине (Python 3.14.7, `cc` = GCC 16.2.0) в ходе написания документа и
приведены с командой, чтобы их можно было воспроизвести.

Документ закрывает два независимых дефекта, у которых общий корень — отказ
не наступает быстро и не наступает как отказ:

- **A. Убегающая рекурсия** не падает быстро и не падает правильно
  (`lang/engine/brat.py`, `lang/engine/brat/runtime.py`, `lang/engine/crt.h`).

Рекурсия уже названа в `docs/design/ARCHITECTURE.md`: §2.5 считает её закрытой
(`docs/design/ARCHITECTURE.md:112-115`).

0. Термины

Держим их строгими, потому что именно размывание этих слов и породило дефект.

- **BRAT-фрейм** — одна активация функции BRAT (вызов именованной `fn`,
  замыкания или метода). Это единица, которую видит язык.
- **Python-фрейм** — кадр CPython. Один BRAT-фрейм стоит *несколько* Python-
  фреймов, потому что интерпретатор проходит `ev → call → run_block →
  run_stmt → _run_stmt → ev` (`runtime.py:1202`, `:1386`, `:1515`, `:388`).
  Сколько именно — измеряемая константа, а не догма (сейчас её зашили как 12;
  `brat.py:27`).
- **Бюджет** — предельная глубина BRAT-фреймов, которую язык гарантирует.
  Это договор языка, а не свойство CPython.
- **Отказ в открытую (fail-open)** — при сбое продолжается как при успехе.
- **Отказ в закрытую (fail-closed)** — при сбое продолжения нет (запрос
  отвергнут, программа остановлена).
- **Fail-safe-and-loud** — при сбое выбирается безопасная ветка, и сбой
  *сообщается* (лог + счётчик), а не растворяется в значении по умолчанию.

1. Инварианты репозитория, которые связывают решение

Решение обязано им соответствовать; это не пожелания, а гейты.

1. **Паритет бэкендов — по stdout и коду выхода.** `test_diff.py:277`
   сравнивает `na == nb and a.returncode == b.returncode` (stdout
   нормализуется, только поля `ts` и CRLF; `test_diff.py:41`). `test_native.py:75-77`
   сравнивает код возврата и stdout. **stderr не сравнивается.** Отсюда прямое
   следствие: любой текст, который программа может *напечатать* (например,
   пойманную ошибку), попадает в сравниваемую поверхность и должен совпадать
   побайтово; текст, уходящий только в stderr, — не должен.
2. **Ошибки — значения** (`SPEC.md:102-117`). `try/catch` ловит рантайм-ошибки
   (деление на ноль, выход за границу, нет ключа) как значения канала, не
   `exit`. Непойманная наверху — `unhandled`/`RuntimeError` + `exit 1`
   (`SPEC.md:108,117`). `main` возвращает `i64` в код выхода (`SPEC.md:250`).
3. **Нет тихих отказов** (`docs/design/ARCHITECTURE.md:206-210`): «каждый отказ
   невозможен, сообщён или обработан — никогда не проглочен в значение по
   умолчанию, выглядящее как успех».
4. **Код прав, доки чинятся** (`docs/README.md:33-36`). Если §2.5
   ARCHITECTURE утверждает паритет, которого нет в коде, — правится док.
5. **Тесты** (skill `brat-lang`): положительный контроль на каждый негативный
   кейс; проверять *диагностику*, а не только код возврата; тест, идущий
   минуты, — сам по себе дефект.

2. A — убегающая рекурсия

2.1 Что происходит сегодня (измерено)

Программа `fn f(n: i64) -> i64 { return f(n + 1) }`, вызванная из `main`.

- **Интерпретатор не отказывает за 45 с.** `timeout 45 python -X utf8
  lang/engine/brat.py /tmp/opencode/runaway.brat` → `EXIT=124` (измерено
  здесь). Снимок стека через `faulthandler.dump_traceback_later(10)`
  показывает, что процесс всё ещё *углубляется* по циклу
  `call → ev → _run_stmt → run_stmt → run_block → call`, то есть не висит и не
  продвигается к отказу — он растёт.
- **Обработчик отказа — мёртвый код.** `brat.py:120-125` при `RecursionError`
  читает `e` (строка `:121`), но `e` не связано: единственное связывание —
  `except OSError as e:` на `:109`, в *другом* `try`. Воспроизведено на
  реальном коде (`mod.run = raise RecursionError`; `mod.run_file(...)`) →
  `UnboundLocalError: cannot access local variable 'e'`. То есть даже если
  `RecursionError` наступит, пользователь получит `UnboundLocalError` вместо
  диагностики про бюджет.
- **Обработчик лжив по смыслу.** Он говорит «the interpreter budget is
  %d BRAT frames» с `RECURSION_BUDGET` (`brat.py:122-124`), хотя фактический
  предел задаёт `sys.setrecursionlimit(RECURSION_BUDGET * 12) =
  1 200 000` Python-фреймов (`brat.py:9,27`), а не 100 000 BRAT-фреймов.
- **Нативный бэкенд счётчика не имеет вообще.** `grep` по
  `crt.h`/`codegen_c.py` (`depth|recursion|budget|100000`) не находит ни
  счётчика глубины, ни константы бюджета. Есть только `BRT_VDFR_MAX = 1024`
  для вложенности `defer` (`crt.h:2414`). Убегающая программа, собранная через
  `cc -O2`, тоже не отказала: `timeout 20 ./runaway` → `EXIT=124` (измерено
  здесь).

Отсюда: утверждения `docs/design/ARCHITECTURE.md:112-115` («Done. Both backends enforce
RECURSION_BUDGET… No longer a parity gap») и `docs/design/PLAN-heavy-items.md:106`
(«Fixed (`ced78cb`) — оба бэкенда сходятся до глубины 100 000») **не
подтверждаются кодом**. Паритет держится только на программах, которые
заканчиваются; на убегающей рекурсии оба бэкенда висят, и ни один не выдаёт
языковую диагностику. Это тот случай, когда по правилу 4 правится док, но
сначала чинится код.

Почему `*12` — это фикция, а не дизайн:

- множитель «Python-фреймов на BRAT-фрейм» — свойство реализации
  интерпретатора, которое меняется от любой правки `ev`/`call`; он не должен
  быть частью языкового обещания;
- `sys.setrecursionlimit` в CPython 3.12+ перестал надёжно ограничивать
  C-стек (для этого есть отдельный предел C-рекурсии), а `brat.py:24` ещё и
  поднимает стек главного потока до 512 МБ (`_STACK_BYTES`, `brat.py:10`),
  то есть снимает предохранитель, который мог бы дать честный отказ раньше;
- `spawn` в интерпретаторе — это `ThreadPoolExecutor` (`runtime.py:1250`), а
  `_run_with_budget` оборачивает только верхний прогон; рабочие потоки `spawn`
  получают стек по умолчанию, и 512 МБ на них не распространяется.

2.2 Что на самом деле значит «бюджет»

Бюджет — это **предел глубины BRAT-фреймов**, одинаковый для языка. Он не
имеет права быть функцией от числа Python-фреймов, размера C-стека или
настроек потока — всё это детали реализации, которые надо спрятать за
маленьким интерфейсом. Текущий код делает наоборот: языковое обещание
выведено из трёх деталей реализации сразу, и потому не выполняется.

Формально: глубина `d` рекурсии BRAT. При `d > BUDGET` язык обязан выдать
*один и тот же* наблюдаемый результат в обоих бэкендах (п. 2.6). `BUDGET` —
константа языка; CPU-стек и множитель Python-фреймов — параметры реализации,
подобранные так, чтобы механизм срабатывал **до** настоящего переполнения, с
запасом на раскрутку.

2.3 Где должна жить проверка

Счёт глубины принадлежит пути *вызова функции BRAT*, а не глобальному
`sys.setrecursionlimit`. Точки входа в интерпретаторе, каждая из которых
кладёт фрейм в среду и зовёт тело:

- именованный `fn` — `call` (`runtime.py:1138-1156`), фрейм:
  `env.append(frame)` на `:1147`;
- замыкание — `run_closure` (`runtime.py:609`);
- метод — `call_method_fn` (`runtime.py:1336`).

Три точки входа — значит шов настоящий, а не гипотетический (принцип «одна
адаптация — шов воображаемый»). Предлагаемый модуль — маленький и глубокий:

```
# runtime.py, рядом с _dfr_stack (runtime.py:696)
_BUDGET = int(env.get("BRAT_RECURSION_BUDGET", ...))  # один раз
_depth = threading.local()

@contextmanager
def frame():            # вход: глубину +1, проверка бюджета
    ...                 # выход (finally): глубину -1
```

Интерфейс — одна операция «войти в фрейм». Всё остальное (сколько Python-
фреймов это стоит, размер стека, TLS против явного счётчика) — реализация.
Проверку вставляют все три точки входа; на превышении они не углубляются
дальше, а поднимают языковую ошибку.

2.4 Варианты

**A1 — языковой счётчик BRAT-фреймов в обоих бэкендах (рекомендуется).**
Интерпретатор считает сам (2.3); `crt.h` получает TLS-счётчик, который
инкрементит/декрементит вход/выход функции, и на превышении вызывает
`vraise("recursion too deep")` (механизм ошибки-как-значения уже есть:
`crt.h:841`, `codegen_c.py:335,346`). `*12` теряет семантическую роль: Python-
лимит ставится «BUDGET × измеренный множитель + запас» и становится
предохранителем, а не определением бюджета.
*Цена:* правка в двух бэкендах + тесты паритета. *Выигрыш:* бюджет становится
настоящим языковым числом; отказ быстрый и одинаковый.

**A2 — латание существующего пути.** Починить `e` в обработчике и снизить
`setrecursionlimit`, чтобы `RecursionError` наступал быстро.
*Цена:* дёшево. *Почему отвергается:* паритета всё равно нет — у C-бэкенда
счётчика нет; множитель остаётся магическим; опора на CPython-предел хрупка
(см. 2.1) и противоречит правилу 4 и §5.1. Это лечение симптома.

**A3 — общий «топливный» бюджет на число шагов/фреймов за прогон.** Ловит не
только рекурсию, но и любые бесконечные циклы.
*Цена:* меняет семантику для всех программ (медленные законные циклы
начинают падать), требует счётчика на каждой итерации, и его тоже надо
держать в паритете. *Почему отвергается сейчас:* это отдельная функция,
которой никто не просил (YAGNI); дефект — именно глубина рекурсии.

**A4 — TCO для хвостовых самовызовов + счётчик для остальных.** `return
f(n+1)` перестаёт расти вовсе.
*Цена:* оптимизация с собственными правилами паритета. *Вердикт:* ценно
позже; бюджет (A1) нужен независимо и первым, потому что без него у A4 нет
страховки на нехвостовой случай.

2.5 Рекомендация

**A1.** Он единственный делает бюджет языковым и сохраняет паритет без
догадок. A2 — обязательная мелкая гигиена *внутри* A1 (мёртвый обработчик
надо убрать в любом случае), но не решение.

Дополнительно, немедленно и дёшево (не зависит от A1):

- `brat.py:120-125` — удалить доступ к `e`; либо убрать специальный
  `except RecursionError` и отдать его общему обработчику `:126-132`, либо
  связать `e`. Специальный текст про бюджет остаётся только если он не врёт
  про число.
- Исправить `docs/design/ARCHITECTURE.md:112-115` и `docs/design/PLAN-heavy-items.md:106`: пока
  счётчика в C нет, это не «DONE», а «интерпретатор только».

2.6 Контракт паритета на исчерпании бюджета

- **Код выхода:** `1` — это непойманная рантайм-ошибка (`SPEC.md:108,117`).
  Оба бэкенда обязаны дать `1`, `test_diff`/`test_native` это фиксируют.
- **stdout:** пусто к моменту отказа (программа не успела напечатать), если
  только программа не ловит ошибку и не печатает сама.
- **Диагностика (stderr):** называет факт и бюджет, например
  `recursion too deep: budget N` — stderr не сравнивается, но обязан быть.
- **Пойманное значение:** если программа ловит исчерпание `try/catch` и
  печатает payload — этот текст попадает в сравниваемую поверхность и
  **обязан совпадать побайтово**. Поэтому payload должен быть стабильной
  строкой без деталей бэкенда (без номера строки, без имени Python-
  исключения), скажем ровно `recursion too deep`. Номер строки допустим
  только в stderr-диагностике. Это прямое следствие правила 1 из §1.

2.7 `defer` и ошибки-как-значения

Отказ на глубине — это обычная рантайм-ошибка в канале, поэтому:

- раскрутка запускает `defer` каждого фрейма: интерпретатор — `run_block` →
  `finally: run_defers` (`runtime.py:1208-1209`, `:703-705`); C — стек
  `vdfr` (`crt.h:2414`), лимит `BRT_VDFR_MAX = 1024`.
- Значит бюджет обязан оставлять **запас на раскрутку**: сработав на
  `d = BUDGET`, механизм должен успешно выполнить `BUDGET` блоков `defer`
  (и не упереться в 1024 по `vdfr`, если defer-ов больше). Проверка, что
  запас достаточен, — часть тест-плана (2.8), а не предположение.
- Раскрутка *уменьшает* глубину, поэтому сама себя не переполняет; риск —
  только в том, что раскрутка требует ещё немного стека поверх уже
  занятого. Отсюда «запас» в бюджет.
- Поймать исчерпание `try/catch` разрешено (правило 2 §1). Это fail-safe:
  программа может деградировать управляемо. Но диагностика обязана быть
  видимой при непойманном случае.

2.8 Тест-план A (быстрый по построению)

Ключевое требование: **тест не идёт минутами**. Условие выполняется только
если бюджет настраиваем (env `BRAT_RECURSION_BUDGET`), при дефолте
`100000`. Тестируется механизм, а не конкретное число.

1. **Отказ быстрый.** `BRAT_RECURSION_BUDGET=2000`,
   `fn f(n)=f(n+1)` → процесс завершается с кодом `1` за < 20 с (жёсткий
   таймаут теста; превышение = FAIL, как `PER_INPUT_BUDGET` в
   `test_fuzz.py:19`). Проверяется, что stderr содержит `recursion too deep`
   (правило «assert the diagnostic»).
2. **Положительный контроль.** Одна и та же программа, рекурсия до `1999` →
   код `0` и ожидаемый stdout. Без этого тест 1 ничего не доказывает
   (`brat-lang`: положительный контроль на каждый негативный кейс).
3. **Паритет отказов.** Тот же убегающий файл в обоих бэкендах: одинаковый
   код (`1`) и одинаковый stdout (пусто). Достаточно компактный кейс, чтобы
   не платить минутами; при желании — отдельный маленький `test_diff`-кейс.
4. **Пойманное значение совпадает.** `try { f(0) } catch e { print(e) }` →
   в обоих бэкендах печатается ровно `recursion too deep` и код `0`.
   Это гейт правила 2.6.
5. **`defer` при отказе.** Программа с `defer log.warn("bye")` и убегающей
   рекурсией: в обоих бэкендах отказ происходит, и виден эффект `defer`
   (или явно задокументировано, что виден).
6. **Живой обработчик.** Регресс на `UnboundLocalError`: тест 1 падает, если
   вместо диагностики про бюджет печатается `UnboundLocalError`.
7. **Выбор числа.** Отдельным замером (не в CI) измерить время отказа при
   дефолтном бюджете; если оно > ~1 с на целевой машине — снизить
   `BUDGET` и зафиксировать новое число в тесте. Число берётся из замера,
   в док не вписывается наугад.

4. Открытые вопросы

- **Число бюджета A.** Оставить `100000` или снизить? Решается замером 2.8.7,
  не рассуждением.
- **Счётчик A: TLS или явный параметр.** TLS (как `_DFR`,
  `runtime.py:696`) не требует протаскивать состояние через все вызовы, но
  требует, чтобы каждый `spawn`-поток получил свой счётчик. Явный параметр
  честнее, но шире по диффу. Решение отложено до реализации.
- **`spawn` в интерпретаторе** не наследует 512 МБ стек (`runtime.py:1250`);
  убегает ли рекурсия внутри `spawn` так же — не измерено здесь.

5. Чего в этом документе не измерено

- Точная скорость отказа интерпретатора на глубине `BUDGET` и число
  Python-фреймов на BRAT-фрейм — не измерены; `*12` здесь не подтверждён.
- Поведение `defer` при исчерпании бюджета — по коду ожидается корректная
  раскрутка (`runtime.py:1208-1209`), но не проверено на практике.
- Реакция `spawn`-потоков интерпретатора на глубокую рекурсию — не
  проверялась.
